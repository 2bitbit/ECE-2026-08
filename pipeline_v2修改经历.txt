================================================================================
pipeline_v2.py 修改经历 —— 量化提速尝试 + 加宽模型 A/B 实验
================================================================================

本文件如实记录对 pipeline_v2.py 的一次探索性修改：先是想解决「int8 在本机
x86 反而更慢」的问题，过程中又顺带做了「加宽模型、多加参数」的对照实验。
两个实验都以「实测数据说话」收尾，结论都很明确，但没有一个是我们最初预期
的方向。这与本项目「诚实评估 > 刷高数字」的原则一致，故单独成文留档。


--------------------------------------------------------------------------------
一、起因：pipeline_v2.py 是什么、想解决什么
--------------------------------------------------------------------------------
项目里除了主流水线 pipeline.py，还出现了一个 pipeline_v2.py（标注
"Optimized"）。经对比，它和 pipeline.py 代码 99% 相同，只改了 3 个与量化/
延迟相关的地方：

  1. 权重量化：per-channel 改成 per-tensor（per_channel=False）。
  2. 量化格式：显式传入 QuantFormat.QOperator（原版不传，用 onnxruntime
     1.28.0 的默认 QDQ）。
  3. 延迟基准里显式设了 graph_optimization_level = ORT_ENABLE_ALL。

逐条核实后判定：
  - 第 2 处是唯一实质改动。QOperator 会把 Quantize/Dequantize 融合进算子
    （变成 QLinearConv），消掉 Q/DQ 节点开销——正是冲着我之前记录的
    「int8 慢，因量化/反量化开销占主导」去的。
  - 第 3 处是无效改动：ORT_ENABLE_ALL 本来就是 onnxruntime 的默认值，
    写了等于没写。
  - 第 1 处 per-channel→per-tensor 是改配置，docstring 里写「减少内存访问
    开销、更快推理」，是断言而非实测。

还发现两个工程问题：
  - docstring 里写 python pipeline_optimized.py，但文件名是 pipeline_v2.py。
  - 输出与 pipeline.py 完全同名（model_*.onnx、results_table.*、
    per_class_metrics.csv、figures/），跑一次 v2 会把 v1 的产物全部覆盖。


--------------------------------------------------------------------------------
二、修改 1：把产物隔离到独立文件夹
--------------------------------------------------------------------------------
做法：在 pipeline_v2.py 里新增 OUT_DIR = v2_output/，并把所有输出路径
（FIG_DIR、两个 .onnx、results_table.csv/md、per_class_metrics.csv、
results_meta.json）都改写到 v2_output/ 下；顺手修正 docstring 里的文件名。

共 8 处编辑。跑之前先确认了根目录原产物没被动（时间戳仍为修改前），跑完后
再次确认 v2 的产物全部落在 v2_output/、根目录 model_*.onnx 未被覆盖。


--------------------------------------------------------------------------------
三、实验 1：QOperator 到底能不能把 int8 拉快？
--------------------------------------------------------------------------------
跑 pipeline_v2.py（per-tensor + QOperator，20 轮，seed=0，本机 Intel/Windows）。
结果：

  指标                  float32       int8
  测试准确率            0.8667        0.8306
  延迟中位数 (ms)       0.30          0.68
  延迟 p99 (ms)         0.34          1.03
  模型大小 (kB)         460.2         118.5
  15ms 判定             FITS          FITS

结论：QOperator 没有带来实质提速。
  - int8 中位数 0.68 ms，与原版 QDQ 的 0.65~0.72 ms 基本一样，仍在噪声区间内。
  - int8 仍约 2.3 倍慢于 fp32（0.30 ms）。
  - 原因：瓶颈不是那几层 Q/DQ 节点的调度开销，而是这个小模型在 x86 上 int8
    算子本身跑得不比 fp32 快，加上输入端 QuantizeLinear / 输出端
    DeQuantizeLinear 是任何量化模型都躲不掉的。换格式救不回来。

附注：这次跑出的 fp32 是 0.8667，与完成说明一致，但 README 写的是 0.8722
（另一台机器/另一数据状态），两者对不上，答辩前需统一口径。


--------------------------------------------------------------------------------
四、插曲：为什么参数只有 11.5 万？多加一点行吗？
--------------------------------------------------------------------------------
模型 = 2 层卷积 + Flatten + 一个 Linear，参数量 115,398，其中 96% 压在
最后一层 Linear（Flatten 把 32×24×24 = 18,432 个特征 × 6 类 = 110,598）。

关键认识：
  1. 作业约束 ≤500k 是「上限」而非「目标」；115k 是故意留的余量。参数多 →
     模型大、FLOPs 多 → 延迟升，而延迟和体积才是两条真正的验收线。
  2. 数据太小（训练集 1080 张、每类 180 张），加参数会加速过拟合。
  3. 准确率天花板不在这里：最弱的 scratches 是 200×200→96×96 降采样把细
     划痕纹理抹掉了，属输入信息损失，加容量变不出被丢掉的信息。

于是做了加宽模型（16→32、32→64 通道，~240k 参数，仍 <500k）的对照实验，
用数据来验证「加参数到底行不行」，而不是嘴上说不行。


--------------------------------------------------------------------------------
五、修改 2：把 v2 换成加宽模型
--------------------------------------------------------------------------------
在 pipeline_v2.py 里新增 task4_model_wide()（通道 16→32、32→64，其余深度/
池化与基线一致，唯一变量是容量），并把 main() 里的模型调用换成它。输出仍
落在 v2_output/（覆盖上次结果）。参数量 240,006，符合预期（≈240k，<500k）。


--------------------------------------------------------------------------------
六、实验 2 结果：加参数「三输」
--------------------------------------------------------------------------------
同一台机器、同一 seed=0、同一 20 轮，唯一变量是通道数。对照：

  指标                  窄模型(115k)   宽模型(240k)   变化
  参数量                115,398        240,006        ×2.1
  fp32 测试准确率       0.8667         0.8250         ↓ 4.2 个点
  int8 测试准确率       0.8306         0.8139         ↓ 1.7 个点
  fp32 延迟中位数 (ms)  0.30           0.92           ×3.1
  int8 延迟中位数 (ms)  0.68           1.05           ×1.5
  fp32 模型大小 (kB)    460.2          947.0          ×2.1
  int8 模型大小 (kB)    118.5          240.3          ×2.0
  最差类 scratches recall 0.650        0.633           反而更差

（窄模型的 int8 数字取自同会话上一次 v2 跑，量化配置同为 per-tensor +
QOperator，故为干净对照。）

结论：
  1. 准确率不升反降（0.8667 → 0.8250）。1080 张训练图撑不起 240k 参数，
     容量翻倍把模型推进了过拟合区；4.2 个点的掉幅远超噪声量级（±0.008），
     方向确定，不是种子抖动。
  2. 延迟翻 3 倍、体积翻 2 倍，正面撞「15ms / 越小越好」的验收线。
  3. 最弱的 scratches 没救回来反而更差（0.650 → 0.633），坐实了「瓶颈是
     96×96 分辨率的信息损失，不是模型容量」。

一句话：在这个小数据 + 低分辨率的任务里，加参数往「过拟合 + 更慢 + 更大」
的方向走，而收益受限于输入信息，加不动。


--------------------------------------------------------------------------------
七、留给答辩的一句话素材
--------------------------------------------------------------------------------
  「我们 A/B 过把模型加宽到 240k 参数（仍 <500k）：测试准确率从 0.867 掉到
   0.825、延迟翻 3 倍、体积翻倍，最弱的 scratches 也更差。说明在 1080 张
   小数据 + 96×96 分辨率下，瓶颈在数据和输入信息、不在容量，所以保留 115k
   窄模型是正确的选择。」

  「我们试过用 QOperator 把 Q/DQ 融合进算子来救 int8 的延迟，实测中位数仍
   是 0.68 ms、约 2.3 倍慢于 fp32，说明瓶颈是 int8 算子本身在这个小模型/
   这台 x86 上并不更快，不是格式问题。」

--------------------------------------------------------------------------------
八、心得
--------------------------------------------------------------------------------
  1. 「看起来更优」不等于「实测更优」：QOperator 方向对，但没兑现提速；
     per-tensor「更快」是断言，数据不支持。断言必须用数据替换。
  2. 容量不是免费的午餐：小数据上，参数越多越容易过拟合，还可能变慢变大。
  3. 先想清楚瓶颈在哪（分辨率/数据），再决定要不要加容量，能少走很多弯路。
  4. 对照实验的可信度来自「只变一个变量」：两次实验都固定 seed、轮数、
     量化配置，只动模型宽度，结论才站得住。
