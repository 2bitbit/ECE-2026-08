================================================================================
项目 1 —— 边缘视觉识别与模型量化（Edge Vision Recognition and Model Quantisation）
完整开发过程记录（从开始到完成）
================================================================================

本文件按时间顺序，如实记录完成这个作业的全过程：每一步做了什么、怎么做的、
为什么要这么做、遇到了哪些困难、最后是怎么解决的。既是对自己工作的复盘，
也是答辩时讲清楚「我为什么这样做」的素材。

--------------------------------------------------------------------------------
一、任务起点：先读懂题目，再动手
--------------------------------------------------------------------------------
最初只是拿到一个目录，里面是脚手架 starter_p1.py 和 6 个 TODO。我先做的是
「查看目录下的文件，思考如何完成项目」，没有急着填代码。

随后补充阅读了教授的要求（要求.txt），明确了验收要点：

  1. 训练一个小型 CNN，识别热轧带钢表面的 6 类缺陷；
  2. 参数量有上限（本项目远低于 50 万，最终只有 115,398 个）；
  3. 按 60/20/20 分层切分，训练/验证/测试不共享样本；
  4. 导出 ONNX，再做 int8 静态量化；
  5. 证明模型能满足树莓派 5 的「单件 15 ms」延迟预算；
  6. 报告每类 precision/recall，量化设置要有理由。

关键认识（为什么要这么定方向）：这份作业的评分强调「诚实的评估」而不是
「刷高数字」。所以后面的所有工作，都坚持一条原则——数字可以不高，但必须
是真的、可复现的、每类指标都摆出来。

--------------------------------------------------------------------------------
二、环境搭建
--------------------------------------------------------------------------------
做了什么：在项目目录下创建 .venv 虚拟环境，安装依赖。
怎么做的：选用 CPU 版 PyTorch（torch 2.13.0+cpu），而非默认的 CUDA 版。
为什么：
  - 部署目标是树莓派（ARM CPU），延迟预算也是按 CPU 单线程来算的；
  - CPU 版安装包只有几百 MB，CUDA 版有 2.5GB 且还需要显卡驱动；
  - 让「在新电脑上一条命令复现」这件事变简单。
依赖清单（requirements.txt）：torch、onnx、onnxscript、onnxruntime、pillow、
numpy、matplotlib。

--------------------------------------------------------------------------------
三、数据集获取（一波三折）
--------------------------------------------------------------------------------
做什么：需要 NEU-DET 数据集（1800 张 200×200 灰度图，6 类各 300 张）。
困难 1：官方数据集在 Kaggle 上，没有 Kaggle 凭据下载不了。
解决：先用 GitHub 镜像（siddhartamukherjee 的 NEU-DET-Steel-Surface-Defect-
  Detection，1770 张）作占位，把整个流水线跑通，等官方数据到了再替换。

困难 2：官方数据解压后，文件名是缩写命名（Cr/In/Pa/PS/RS/Sc），而且
  和全类名对不上。
解决：建立缩写到全类名的映射（Cr→crazing、In→inclusion、Pa→patches、
  PS→pitted_surface、RS→rolled-in_scale、Sc→scratches），整理成
  NEU-DET/<类名>/ 的目录结构，加载器同时兼容 .bmp 和 .jpg。

最终：用官方 1800 张数据跑出正式结果，并更新了所有文档里的数字。

--------------------------------------------------------------------------------
四、脚手架任务（starter_p1.py 的 6 个 TODO）
--------------------------------------------------------------------------------
逐个补齐了 6 个 TODO，并理解每一处的意义：

  任务 1  像素归一化：arr / 255.0，把 0~255 缩到 0~1，利于训练收敛。
  任务 2  训练/测试 80/20 切分：int(0.8 * len(idx))。
  任务 3  准确率计算：(preds == truth) 的均值。
  任务 4  补全最后一层：nn.Linear(n_features, 6)，输出 6 类 logits。
  任务 5  训练步：loss.backward() 和 opt.step()，完成反向传播与参数更新。
  任务 6  计时：perf_counter 差值 × 1000 转成毫秒。

额外的发现（重要）：脚手架的 load_real() 有一个「重复计数」的 bug——同一张图
会被读两次，导致 1770 张变成 3540 张，更糟的是同一张图会同时进入训练集和
测试集，造成数据泄漏。用集合去重 + 扩展名无关的加载方式修复了它。

--------------------------------------------------------------------------------
五、主流水线 pipeline.py 的设计
--------------------------------------------------------------------------------
做什么：新建一个 pipeline.py，把「加载 → 切分 → 训练 → 导出 ONNX → 测延迟 →
int8 量化 → 每类指标 → 生成报告」串成一条命令 python pipeline.py 就能跑完。
为什么：作业的验收标准之一就是「一条命令可复现」，把全流程收敛到一个入口，
答辩时也好讲清楚每一环。

关键设计决策（怎么做 + 为什么）：
  - 60/20/20 分层切分：按类别分别切，保证每个类别在三个集合里都有，且
    任何一个样本不会同时出现在两边（训练/测试零重叠）。
  - 固定随机种子 seed=0：让结果可精确复现，重跑数字一致。
  - ONNX 导出：固定 batch=1（树莓派一次处理一个工件，这正是部署形状），
    external_data=False（权重留在单个 .onnx 文件里，报的模型大小才是真的）。
  - 延迟基准：单线程、batch=1，30 次预热 + 100 次计时，取中位数和 p99。

--------------------------------------------------------------------------------
六、量化方案与理由
--------------------------------------------------------------------------------
校准集：120 张（每类 20 张），全部取自训练集、不碰测试集。
  —— 足够覆盖每一类和明暗纹理范围，又小到量化很快。
校准方法：percentile 百分位截断。
  —— 忽略个别异常像素，避免它们把范围撑大、浪费精度。
权重：per-channel（逐通道）QInt8。
  —— 每个卷积核单独一个 scale。实测 per-tensor 对照：0.8250 vs 0.8306，仅差 2 张测试图，说明「精度更高」的小模型优势未显现，两者可互换。
激活：QUInt8 非对称。
  —— ReLU 输出 ≥ 0，无符号范围不浪费负半轴。

--------------------------------------------------------------------------------
七、遇到的所有困难与解决过程（重点复盘）
--------------------------------------------------------------------------------
1. ModuleNotFoundError（torch/onnx 等找不到）
   原因：新环境没装依赖。解决：建 .venv，用 --index-url 装 CPU 版 torch，
   其余 pip install -r requirements.txt。

2. UnicodeEncodeError: 'gbk' codec can't encode '✅'
   原因：Windows 控制台默认 GBK 编码，torch 的 ONNX 导出器打印了 ✅ 等
   emoji，直接崩。解决：脚本开头加
     sys.stdout.reconfigure(encoding="utf-8", errors="replace")
   并包 try/except 以防非 Windows 环境没有这个方法。

3. dynamic_axes 已废弃（dynamo=True 时报错）
   原因：新版 torch 导出器默认走 dynamo，旧的 dynamic_axes 参数不再适用；
   一开始改用 dynamic_shapes 又因 key 名不符报错。
   解决：干脆去掉动态 batch，固定 batch=1——这本来就符合树莓派的部署场景。

4. quant_pre_process 报 "Incomplete symbolic shape inference"
   原因：动态 batch 让形状推理推断不出静态形状。解决：导出时固定 batch=1，
   并在量化函数里加 try/except 兜底。

5. float32 模型只有 9.9 kB
   原因：torch 默认把大权重拆到外部 .data 文件，.onnx 本体只剩图结构。
   解决：export 时 external_data=False，让权重留在单个文件里，报的模型
   大小（460 kB）才是真实、诚实的。

6. 目录里多出临时文件（*.data、sym_shape_infer_temp.onnx 等）
   原因：量化预处理会在当前目录留垃圾。解决：把 quant_pre_process 包进
   tempfile.TemporaryDirectory，并显式清理 sym_shape_infer_temp.onnx。

7. 控制台表格类名串行（"scratchespitted_surface"）
   原因：表格字段宽度不够，两个类名挤在一起。解决：把格式宽度从 >12
   加宽到 >16。

--------------------------------------------------------------------------------
八、两个隐蔽 bug 的发现与修复（最有价值的复盘）
--------------------------------------------------------------------------------
8. 【数据泄漏】load_real 重复计数（前面第四节已述）
   后果：同一张图同时进入训练和测试，准确率是虚高的。已修复。

9. 【校准集索引 bug】pipeline.py 里 calib_X = X[calib_idx]
   现象：导出校准集时核对代码，发现 calib_idx 是「训练子集内的位置」，
   却拿去索引「全量数组」。
   实测当时的校准集分布是 33/34/33/20/0/0——rolled-in_scale 和 scratches
   两个类一张校准图都没有！这跟文档里「每类 20 张、只来自训练集」完全不符。
   解决：改成 calib_X = X[tr[calib_idx]]，先通过 tr 把子集位置映射回全量
   索引。修复后校验，每类确实都是 20 张、全部来自训练集。

10.【默认参数 bug】epochs 默认是 10，但文档数字是 20 个 epoch 的结果
   现象：重跑流水线，float32 只有 0.7583，和文档写的 0.8667 对不上；
   但两次重跑结果完全一致，说明训练本身是确定的、可复现的。
   排查：扫了 15/20/30/40 个 epoch，发现 0.8667/0.8250 正好对应 20 个 epoch。
   结论：文档数字没错，是代码默认值写错了。把默认改成 20，一条命令即复现。

这两个 bug 都是「文档说的」和「代码实际做的」不一致，且都会影响诚实的
评分。发现它们靠的是「导出前先核对、重跑前先怀疑」，这正是这份作业最想
训练的能力。

--------------------------------------------------------------------------------
九、诚实评估与结论（最终数字，本机 Intel CPU / Windows 10）
--------------------------------------------------------------------------------
指标                     float32         int8
测试准确率               0.8667          0.8250
最差类 recall            scratches 0.65  scratches 0.67
模型大小                 460 kB          124 kB（缩小 3.7 倍）
延迟中位数 (ms)          0.29            0.72
延迟 p99 (ms)           0.33            1.14
15 ms 预算判定           FITS            FITS

三条诚实的结论（答辩可直接用）：
  1. int8 把模型缩小约 4 倍，但延迟反而变慢（0.33 → 1.14 ms）。原因是模型
     太小，量化/反量化开销占主导，且本机 x86 CPU 没有 int8 加速指令；两者
     都远低于 15 ms 预算。
  2. 量化后掉得最多的是 pitted_surface（recall 0.817 → 0.700），因为它和
     patches 视觉相近，量化模糊了细小凹坑的细节。
  3. 基线最弱类是 scratches（recall 0.65），因为 200×200 缩到 96×96 抹掉了
     细划痕的纹理；量化后它仍是 recall 最低的类。

十、复现方法（新电脑上一条命令跑通）
--------------------------------------------------------------------------------
  python -m venv .venv
  .venv\Scripts\activate                      （Windows）
  pip install torch --index-url https://download.pytorch.org/whl/cpu
  pip install -r requirements.txt
  python verify.py                            （应输出 PASS）
  python pipeline.py                          （一条命令重新生成全部输出）

准确率因固定 seed=0 可精确复现；延迟取决于新机器 CPU，会略有不同，但都
远低于 15 ms。

--------------------------------------------------------------------------------
十二、心得与反思
--------------------------------------------------------------------------------
1. 先读懂题目和评分标准再动手，比急着写代码重要得多。
2. 「可复现」不是口号：固定随机种子、固定 batch、固定切分，缺一不可。
3. 诚实评估是底线：int8 在这个平台上确实更慢，那就如实说慢、并解释为什么，
   而不是藏起来。
4. 最隐蔽的错误往往藏在「文档说的」和「代码做的」不一致里；导出任何数据
   前都值得核对一遍。
5. 遇到报错不要绕：GBK 编码、动态形状、外部权重、临时文件……每一个都有
   明确的原因和对应的解法，记录下来下次就能秒查。
